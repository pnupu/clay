# A playground inside this app (prototype B)

When I ask for a playground for a page, a component or a motion of THIS repository, build it inside the app, with the real code. Do not copy the component into Clay's hosted preview: a copy is not the thing. Work in the checkout you are in: no git worktree, no branch, no commit, no push.

The kit is two files in `KIT_DIR` (the path is at the end of this file): `clay-playground.tsx` (one client component: a stage, a few controls, a level switch, Settle) and `clay-settle-route.ts` (a dev-only route that writes what I settle to a file). Read the types at the top of `clay-playground.tsx` before you write the page.

A component is never alone: a change to it is made at one of three levels, and each level changes other places too. The playground must show that before anything is written.

1. Read the real component, its props and its variants. Search the whole codebase for its uses (`grep`), not one place. Read the theme: the Tailwind theme and the CSS variables (`globals.css`, `@theme`, `tailwind.config`). Find the app's root layout and providers (theme, fonts, global CSS): the playground must render under the same ones.
2. Copy `clay-settle-route.ts` to `<app>/src/app/api/clay-settle/route.ts` and `clay-playground.tsx` to `<app>/src/app/clay/_kit/clay-playground.tsx`.
3. Add the dev-only route `<app>/src/app/clay/<id>/page.tsx`. First line of the component: `if (process.env.NODE_ENV === "production") notFound();`. Put it where no sign-in or data guard applies (top-level `app/clay/`, under the root layout). `ClayPlayground` takes functions, so the file that calls it starts with `"use client"` (put the page body in a client file next to `page.tsx` when the page itself must stay a server component).
4. `uses`: at least three real places where the component is used, the one I asked about first. For each: `file` is the path from the repository root with the line (`src/app/x/page.tsx:42`), and `render(a)` returns the REAL component imported from its real path, with the props, children and the markup around it copied from that call site (fixtures where it needs data; no network, no sign-in). Put `className={cn(<the call site's classes>, a.className)}` and `style={a.style}` on the component. For a prop, `a.values` holds only the controls I moved, and nothing for a use that does not change, so every use keeps its own props: `variant={(a.values.variant as <the prop's type> | undefined) ?? <the call site's own prop>}`. `sets`: the style properties that this call site always sets itself with its own class (not under `hover:` or `md:`), named as the `css` of your scale controls (`sets: ["borderRadius"]` for a call site with `rounded-none`). At the level `variant` such a call site keeps its own value in the real code, so the kit leaves those controls out for that use and the stage shows it unchanged. Choose the uses so that every level shows a difference: other uses of the same variant, and at least one use of another variant or one that a level does not reach.
5. `levels`: only the levels that are real for this component, narrowest first. Each has `target` (what changes, exactly), `files` (the files the hand-back edits at this level), `uses` (the ids of the shown uses that change) and `others` (the files with more uses that change and are not shown; list them all, from your search).
   - `instance`: a class or a prop at the one call site I asked about. `uses` is that one use.
   - `variant`: the variant definition in the component file (for example the `cva` variant). `uses` are all shown uses of that variant.
   - `token`: a theme token or CSS variable. `uses` are all shown uses bound to it.
   A level that a rule of the repository forbids (for example "do not edit `src/components/ui/`") stays in the list with `blocked: "<the rule>"`: it is shown and cannot be chosen. Leave out a level that does not exist.
6. `controls`: 3 to 6, each one thing I asked about. `initial` is what the code has now, so the page opens on today's look.
   - Spacing, radius and colour are `type: "scale"`: `options` are the project's own scale classes and token classes, in order (`px-2`, `px-2.5`, `px-3`; `rounded-md`, `rounded-lg`; `bg-background`, `bg-muted`), `initial` is the class the code has now, and `css` is the style property for a value off the scale (`paddingInline`, `borderRadius`, `backgroundColor`). I can type a raw value; the kit marks it off-scale. Write every option as a full class string in the page, so that Tailwind compiles it.
   - A control with `token: "--radius"` belongs to the level `token`: a slider with `unit` or a colour whose `initial` is the token's value now. The kit sets the variable on the page root. Add one for each token of the level.
   - Other things (a variant prop, a state, a duration) are `select`, `toggle` or `slider`. A use reads one as `a.values.<id> ?? <the call site's own value>`, never without the fallback: a control I did not move is not in `a.values`.
   Show the states side by side when I ask about states. Motion: bind duration, easing and distance to the real classes, props or variables, and add a Replay button.
7. `outputs(v, level)` returns the code-ready text for the values now at that level, in the project's own form: the class string, the props, the token line. It is what you will write at hand-back.
8. Start the dev server in the background if none runs, load the route once with `curl` and check for HTTP 200 and no error in the server log. Then give me the URL, say which levels I can choose and what each one changes, and stop. Do not change the real component yet.
9. When I say I am done: read `<app>/.clay/settled/<id>.json`. It holds `level`, `target`, `files`, `uses` (`changed`, `unchanged`, `changedNotShown`), `values`, `initial`, `changed` (the controls I moved), `onScale`, `tried` (the range I tried) and `outputs`.
   - Edit ONLY the files in `files`, and in them only what `target` names: at `instance` the one call site, not its neighbours in the same file and not the component; at `variant` the variant definition, not a call site; at `token` the token's value in the theme file, not a class.
   - Write only the controls in `changed`, in the project's own form: scale classes, props, tokens. A raw or bracket value (`rounded-[14px]`, a hex colour) is allowed only where `onScale` is `false` for that control, because I chose it; a token keeps the notation of the theme file.
   - Run the project's typecheck (`npx tsc --noEmit -p .` or the project's script) and fix what you broke.
   - Delete the playground: `src/app/clay/`, `src/app/api/clay-settle/` and `.clay/`. The diff must hold only the edit.
   - Report: the level, the file and line you edited, which uses changed (shown and not shown, with a count), which shown uses did not change, the range I tried, every off-scale value, and the typecheck result.

Sharing with someone else, and choices that rest on prices or web facts, still go through Clay's hosted playground (`create_playground`).
